# /dev — 完整开发流程

## 触发条件

AI 自动路由或用户显式调用 `/dev`。适用于：
- 新功能开发
- 大规模重构
- 架构变更
- 涉及多文件的复杂修改

## ⚠️ 铁律（补充，全局铁律见 GEMINI.md）

1. **禁止跳过检查点** — 每个 ⛔ 检查点必须等用户确认后才能继续，不能自行推进。
2. **完成后必须归档** — 步骤 9 不是可选项，是必须执行的最后一步。

## 执行步骤

### 1. 读取项目上下文、记忆与规范

**必须先读取以下文件**，了解项目当前状态：
- `.agents/context/architecture.md` — 技术栈、目录结构、编码规范
- `.agents/context/active-tasks.md` — 进行中的任务
- `.agents/context/feedback.md` — 用户纠正和行为偏好
- `.agents/context/user-preferences.md` — 用户角色与沟通偏好
- `.agents/specs/` 下与当前任务相关的 spec 文件 — 系统行为规范

如果这些文件不存在，先执行 `/init`。

⚠️ 读取 spec 时，如果发现与实际代码不符，**先更新 spec 再继续工作**。

**智能检索归档**：读取 `.agents/archive/_index.md`，根据当前任务描述，只选出 **≤5 个最相关**的归档文件阅读，不要全量加载。

### 2. 需求分析

- 理解用户需求的边界和目标
- 阅读所有相关代码文件
- 识别关键约束与风险

> ⛔ **必须按以下格式输出，缺一不可：**

```
## 已读文件
- `path/to/file1` 第X-Y行
- `path/to/file2` 第X-Y行

## 需求理解
[用自己的话复述需求，确认理解无误]

## 关键代码引证
[涉及的现有代码片段原文]

## 约束与风险
[识别出的限制条件和风险点]
```

> ⛔ **检查点 1**：等待用户确认需求分析无误后继续

### 3. 技术决策澄清

分析需求中存在的**隐含决策点**，以问题清单形式主动提出：

> ⛔ **必须按以下格式输出：**

```
## 需要确认的技术决策

### 🔴 阻塞性决策（必须确认才能继续）
1. [决策问题]
   - 选项 A：[描述] — 优势/劣势
   - 选项 B：[描述] — 优势/劣势
   - 建议：[你的推荐 + 理由]

### 🟡 非阻塞性决策（可先按默认推进，后续调整）
1. [决策问题]
   - 默认方案：[描述]
   - 备选方案：[描述]
```

- 如果没有隐含决策点，明确说"无需额外决策"并跳过
- 关注：数据结构选择、状态管理方式、模块边界划分、性能策略等

> ⛔ **检查点 2**：等待用户逐条回答后继续

### 4. 架构设计

- 从全局视角设计方案，确保与现有架构兼容
- 明确模块职责划分和接口定义
- 评估性能、可维护性、扩展性
- 输出：**架构设计方案**（中文，提交用户确认）

> ⛔ **检查点 3**：等待用户确认设计方案后继续

### 5. 编写实现方案

- 需要修改/新增/删除的文件清单
- 核心接口和数据结构定义
- 关键实现逻辑说明
- 风险点和应对策略
- 输出：**implementation_plan.md**

> ⛔ **检查点 4**：等待用户审核方案后继续

### 6. 任务拆解

- 将方案拆解为可独立执行的最小任务
- **每个任务必须包含验收标准**，格式如下：

```markdown
- [ ] **任务描述**
  - 验收：[可验证的具体断言，如：调用 X 方法返回 Y 结果]
  - 验收：[不会触发的副作用或边界条件]
  - 预估：~Xmin
```

- 验收标准不要求写正式测试用例，但必须是**客观可判断**的
- 输出：**task.md**（带验收标准的 checkbox 格式）

### 7. 逐条执行

严格按任务清单逐条实现：
- 每完成一条，在 task.md 中标记 `[x]`
- 实现前**必须先阅读**要修改的文件
- **每完成一个任务后，立即微审查**：
  - 改动是否满足该任务的验收标准
  - 是否引入编译错误或明显逻辑错误
  - 是否破坏已完成任务的验收标准
- 每完成 3-5 个任务后，进行一次**跨任务一致性检查**

### 8. 最终代码审查

所有代码修改完成后，**必须**重新阅读每个被修改的文件，执行**全量兜底审查**：
- 检查逻辑正确性（必须引用具体代码行）
- 检查与现有代码的兼容性
- 检查命名规范一致性
- 检查是否引入新的依赖或副作用
- **逐条核对 task.md 中的验收标准是否全部满足**

> ⛔ **必须按以下格式输出审查报告：**

```
## 已审查文件
- `path/to/file` — ✅ 无问题 / ⚠️ 发现问题

## 验收标准核对
- [x] 任务1 验收标准 — ✅ 通过
- [x] 任务2 验收标准 — ✅ 通过

## 发现的问题（如有）
- 问题描述 + 具体代码行引用 + 修复建议

## 变更摘要
- 本次共修改 X 个文件，新增 X 行，删除 X 行
```

> ⛔ **检查点 5**：将审查报告和变更摘要提交用户最终审核

### 9. 验证

- 运行相关测试（如有）
- 手动验证关键路径
- 确认功能符合需求

### 10. 归档 + 更新规范

完成后自动归档：
1. 在 `.agents/archive/` 对应分类下创建归档文件（≤100行），**必须使用 frontmatter**：
   ```yaml
   ---
   name: 任务标题
   description: 一句话描述——用于未来判断相关性，要具体
   type: feature | bugfix | refactor
   date: YYYY-MM-DD
   status: completed | partial
   ---
   ```
2. 更新 `.agents/archive/_index.md`
3. 更新 `.agents/context/active-tasks.md`（移除已完成任务）
4. **更新 specs/**：
   - 涉及已有 spec 的模块 → 更新对应 spec 文件
   - 涉及新模块且复杂度 ≥3 个文件 → 创建新 spec + 更新 `specs/_overview.md`
   - 只是小修改（1-2 个文件）且无对应 spec → 不创建
5. 如有架构级变更，更新 `.agents/context/architecture.md`

### 11. 自动提取记忆

归档完成后，回顾本次对话，自动提取并写入记忆（如有新发现）：
- 用户纠正/确认的行为 → 写入 `context/feedback.md`
- 新了解的用户背景/偏好 → 写入 `context/user-preferences.md`
- 提到的外部资源链接 → 写入 `context/references.md`
- 重要技术决策及原因 → 写入 `archive/decisions/`

只保存从代码中无法推导的信息，不保存代码模式/架构/Git 历史。
