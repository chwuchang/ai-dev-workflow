# /review — 代码审查流程

## 触发条件

AI 自动路由或用户显式调用 `/review`。适用于：
- 审查项目中已有代码的质量
- 审查他人提交的代码或 PR
- 对特定模块/文件做深度审查
- 代码合并前的最终检查

## ⚠️ 铁律（补充，全局铁律见 GEMINI.md）

1. **必须先读再评** — 所有审查意见必须基于实际阅读的代码，禁止凭印象或猜测评价。
2. **引证原文** — 每条审查意见必须附带具体代码行引用，不能笼统评价。
3. **区分审查模式** — 必须先明确本次是全量审查还是增量审查，再决定阅读深度。
4. **问题优先输出** — 审查报告先列问题，再给摘要和正向评价。
5. **长期记忆即时写入** — 一旦触发长期记忆条件，在当前回复后立即更新对应 `context/` 文件。

## 与任务工作区的关系

- `/review` 是**独立审查命令**
- 默认只输出审查结论，**不写入** `.agents/tasks/<task-id>/review.md`
- 只有当审查对象明确对应某个活跃任务，且用户明确要求回写时，才将结果写入该任务目录
- 标准输出骨架位于 `.agents/workflows/_templates/review-report.template.md`

## 执行步骤

### 1. 读取项目上下文

**必须先读取**：
- `.agents/context/architecture.md` — 技术栈和编码规范
- `.agents/context/feedback.md` — 用户行为偏好
- `.agents/context/user-preferences.md` — 用户稳定偏好和沟通习惯
- `.agents/specs/` 下与审查范围相关的 spec 文件（如有）

### 2. 确认审查范围

> **必须先确认以下信息：**

```
## 审查范围
- 目标：[具体文件/模块/PR/分支]
- 审查模式：全量审查 / 增量审查
- 重点关注：[用户指定的关注点，如有]
```

- 如果用户已在请求中明确指定了审查目标和范围，可跳过此检查点直接进入阅读
- 如果用户没有明确范围，主动询问
- 如果是 PR 或 diff 审查，先获取变更文件列表
- 如果是增量审查，只审查变更部分及其**必要上下文**
- 如果是全量审查，完整阅读指定文件或模块

> ⛔ **检查点**：仅当审查范围不明确或需要 AI 补充确认时，等待用户确认后继续

### 3. 按模式阅读代码

#### 全量审查

- **完整阅读**每个待审查文件
- 大文件分段阅读，确保覆盖全部
- 对照 `architecture.md` 与相关 `specs/` 检查一致性

#### 增量审查

- 先读取 diff、变更文件列表或用户指定的改动范围
- 重点阅读变更代码
- 只补充读取判断问题所必需的上下文，不机械扩展到整个模块
- 如果发现局部改动无法脱离全量上下文判断，应明确说明并升级为更深审查

### 4. 输出审查报告

> ⛔ **必须按以下格式输出，缺一不可：**

- 优先以 `.agents/workflows/_templates/review-report.template.md` 为骨架生成审查报告

```
## 🔴 阻塞性问题（必须修复）
### [问题标题]
- **文件**：`path/to/file` 第 X-Y 行
- **代码**：
  ```
  [粘贴问题代码原文]
  ```
- **问题**：[问题描述]
- **建议**：[修复方案]

## 🟡 建议改进（推荐修复）
### [问题标题]
- **文件**：`path/to/file` 第 X-Y 行
- **问题**：[描述]
- **建议**：[改进方案]

## 🟢 可选优化（锦上添花）
- [优化建议]

## 审查覆盖
- 审查模式：[全量 / 增量]
- 审查文件数：X
- 审查范围：[具体文件/模块/PR/分支]
- 未覆盖部分：[如有，明确说明]

## 审查摘要
- 总体评价：[一句话概括代码质量]

## ✅ 做得好的地方
- [值得保持的实践]
```

- 如果某个等级没有问题，也必须显式写“无”
- 审查维度按以下优先级排序：
  1. **正确性** — 逻辑错误、边界问题、空引用、竞态条件
  2. **安全性** — 输入校验、权限检查、敏感数据暴露
  3. **架构一致性** — 是否符合现有框架约定和模块职责划分
  4. **可维护性** — 命名规范、代码重复、模块耦合度
  5. **性能** — 明显的性能问题（不吹毛求疵）

### 5. 用户确认

> ⛔ **检查点**：将审查报告提交用户确认

- 用户可要求对特定问题进一步展开分析
- 用户可要求直接修复阻塞性问题（此时升级为 `/fix`）
- 如果用户要求将本次审查结果回写某个活跃任务目录，再执行写入

### 6. 条件提取记忆与规范

审查过程中如果发现值得长期记录的信息：
- 发现反复出现、未来仍会重复踩坑的模式问题 → 建议更新 `specs/` 中的规范
- 用户纠正审查标准（"这个不算问题"）且未来仍适用 → 写入 `context/feedback.md`
- 用户明确偏好的审查风格或关注顺序 → 写入 `context/user-preferences.md`

只记录长期有效信息，不记录一次性审查偏好或当前对话临时状态。
